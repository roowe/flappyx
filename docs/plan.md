## 1. 目标与范围

参考 `/Users/luoliwei/myproject/CrossGameEngine` 的目录组织，分别使用 Cocos Creator、Godot、Phaser、Three.js 和 Unity 实现同一个 Flappy Bird。五个版本共用素材、玩法参数与验收用例，能够独立启动，并可对照比较画面、手感和引擎接入方式。

玩法和美术参考 `/Users/luoliwei/github/ejoy2d/examples/flappybird.lua`。ejoy2d 本期作为参考实现，不增加第六个工程。

首版完成：准备界面、点击起飞、重力下落、上下水管、背景与地面滚动、碰撞死亡、计分、结算、重新开始、最高分本地保存，以及窗口缩放和前后台暂停。先交付本机可玩版本；移动端安装包、线上发布、排行榜、广告、账号和联网不进入首版。

CrossGameEngine 用作组织与启动方式参考。FlappyX 只建立这款小游戏需要的输入、渲染、存储和主循环适配，不引入角色、背包、云存档等通用框架模块。

## 4. 资源准备方案

1. 将已确认的鸟素材文件复制到 `shared/assets/source/`，记录来源路径、源仓库提交号、文件哈希和许可证信息。保留原文件，不修改 ejoy2d 工程。素材单独的授权来源若无法核实，记录为待确认项，在对外发布前解决。
2. 使用 `uv` 管理 Python 转换工具，读取 PPM 的预乘 RGB 和 PGM 的 Alpha，还原为 straight Alpha 的标准 RGBA PNG；检查尺寸一致、透明边缘和颜色表现。
3. 根据 `birds.lua` 的 `src` 与 `screen` 顶点对应关系恢复方向。水管存在旋转存放，不能只取包围矩形裁剪；输出方向统一的精灵，保留锚点和显示尺寸。
4. 首版导出鸟的三个独立帧、天空、地面、水管头和水管身体。水管头保持比例，身体单独延伸或平铺，避免把开口一起拉长。无关的 `Spaceship.png` 等图块不进入运行资源。
5. 建立统一精灵元数据，包含逻辑 ID、文件名、原始尺寸、锚点和动画序列。确认 ejoy2d 的定点坐标、矩阵缩放与像素单位后再计算显示尺寸，不直接把 Lua 顶点值当成像素。
6. 生成可查看的资源预览图，对照原示例核对鸟、水管方向、天空/地面拼接与透明度；五个引擎统一使用最近邻采样并关闭不必要的 mipmap。

资源完成标准：转换可重复执行；输入文件未改变；透明度与旋转正确；鸟帧和水管可以直接导入五个引擎；资源来源及待确认事项可查。

## 5. 统一玩法基线

### 5.1 画布与运动

先保留示例的 1024×768 横屏逻辑画布，等比缩放并留边，窗口变化不改变水管间距、鸟的速度或碰撞范围。竖屏玩法以后单独调参。

逻辑坐标原点在左上，x 向右、y 向下；鸟和水管位置统一以中心点表示。显示保留逻辑坐标的小数部分，`render.roundPixels = false`，采用最近邻采样。Unity/Three.js 等坐标转换只出现在渲染适配层。

首版采用 30 Hz 固定逻辑步长，渲染频率独立。以下数值来自参考示例，已通过素材核对、TS fixtures 与 Phaser 浏览器闭环验证，冻结为共享配置 `phaser-v1`。

| 参数 | 首轮基线 | 说明 |
| --- | --- | --- |
| 逻辑画布 | 1024×768 | 与 Lua 示例一致 |
| 鸟的固定 x | 350 | 鸟只在 y 方向移动 |
| 鸟、水管缩放 | 2.5 | 结合素材元数据计算显示尺寸 |
| 初始高度 | 距落地位置向上 50 | 落地位置由地面顶边和鸟的半高计算 |
| 起飞速度 | y 方向 -13.5 单位/tick | 按下时覆盖速度，不累加冲量 |
| 重力 | y 方向 +1.5 单位/tick² | 与固定 tick 绑定 |
| 水管、地面速度 | 向左 8 单位/tick | 相同滚动速度 |
| 天空速度 | 向左 2 单位/tick | 形成视差 |
| 水管通道高度 | 200 | 80×2.5 |
| 水管间净距 | 190 | 中心间距为水管宽度 + 190 |
| 首组水管中心 x | 1224 | 画布宽度 + 200 |
| 死亡后重开保护 | 15 tick，即 0.5 秒 | 防止同一次输入误触重开 |

每 tick 顺序统一为：消费输入 → 移动背景/水管 → 更新鸟位置与速度 → 按优先级判断碰撞 → 在仍存活时计分 → 在仍存活时回收水管 → 发布事件。鸟的运动按“位置加当前速度，再加重力”更新。碰撞优先级为地面 → 顶部 → 上管 → 下管；同 tick 同时撞地面和下管时，直接落地结算，死亡优先于得分。卡顿最多补跑 5 tick，丢弃多余完整 tick 的积累时间，保留不足一个 tick 的小数部分；后台恢复时清空积累时间，避免突然快进。

### 5.2 状态与输入

| 状态 | 行为与转换 |
| --- | --- |
| `ready` | 显示开始提示；首次 flap 同时开始游戏并起飞 |
| `playing` | flap 起飞；每组水管成功通过后加 1 分；碰管或顶部进入 `dying`，碰地面当 tick 直接进入 `gameOver` 并夹到 y=514 |
| `dying` | 停止水管和背景；禁用 flap；鸟下落到地面后进入 `gameOver` |
| `gameOver` | 显示本局和最高分；保护期结束后允许重新开始 |
| 暂停标记 | 失焦或进入后台时冻结逻辑；回前台显示继续入口，由玩家操作恢复 |

桌面空格、鼠标主键及触摸开始统一映射为 `flap`；忽略键盘自动重复，触摸与合成鼠标事件去重，每 tick 最多消费一次 flap。UI 按钮阻断玩法输入，重开按钮不会同时触发一次跳跃。

### 5.3 碰撞、计分和生成

- 水管碰撞使用鸟的 64×44 轴对齐碰撞盒，旋转只影响视觉。水管使用上下两个矩形，碰到边界也视为碰撞。
- 地面和顶部使用鸟未旋转的 85×60 显示边界。按地面、顶部、上管、下管的顺序判定；地面命中当 tick 直接进入 `gameOver`，中心夹到 y=514、速度归零。管道或顶部命中进入 `dying`，速度设为 0，死亡下落从下一 tick 开始。
- 水管右边缘严格小于鸟碰撞盒左边缘时视为完全通过；默认左边缘为 `350 + offsetX - 32 = 318`，不使用 85×60 显示边界的左边缘。只加一次分，用 `passed` 标记记录；死亡同 tick 不计分。
- 水管开口中心范围根据地面顶边、半通道高度和上下安全边距计算；非法配置在加载时明确报错。初始只生成七组，右边缘严格小于 0 才回收；回收在该 tick 碰撞和计分完成后执行，只消费一个新高度，接到队尾并重置 `passed`。
- 正常游戏使用可设种子的随机源。跨语言采用同一明确的 32 位随机算法与种子约定；验收用例优先直接提供水管序列，避免引擎原生随机数影响比较。
- 最高分使用引擎各自的本地存储。统一数据字段为 `schemaVersion`、`bestScore`，首版不做存档互导。若后续增加保存时间，采用 Unix 毫秒时间戳，界面按东八区显示。

这里有意规范了参考示例的部分行为：首次输入直接起飞、明确准备/死亡/结算状态、以鸟碰撞盒代替中心点碰撞、完全通过水管后计分，以及明确顶部碰撞。五引擎复用这些规则，不逐个复刻示例中的边界差异。

## 7. 验收方式

### 7.1 共享逻辑验证

仅编写能发现实际玩法差异的少量用例：

- 固定 tick 的起飞与下落轨迹。
- 一组水管仅计分一次，以及碰撞和通过发生在同 tick 时不加分。
- 死亡输入保护、结算和重开后的分数/速度/水管状态重置。
- 固定输入 tick、固定水管序列下，TS 与 C# 的死亡 tick、最终分数和水管顺序相同；位置/速度误差不超过 0.001 逻辑单位。
- 同 tick 地面与水管重叠的优先级、七组队列回收、碰撞盒偏移、暂停/恢复和最多五个补 tick。M1 的 Python 逐 tick 参考校验不替代各生产内核独立执行这些 fixtures。

共享内核使用双精度数值。30/60/120 FPS 渲染回放同一组逻辑输入，结果应一致；输入回放按 tick 注入，不依赖墙钟时间。

### 7.2 每个引擎的实机检查

- [ ] 能按 README 从工程或本地构建启动，关键贴图完整。
- [ ] 可以从准备状态开始，飞过水管，死亡结算并重新开始。
- [ ] 鸟帧、水管方向、透明边缘正确，地面/天空循环没有明显缝隙。
- [ ] 空格、点击、触摸在相应运行环境生效，无重复起飞和 UI 穿透。
- [ ] 碰撞边界、完全通过计分、输入保护与基准规则一致。
- [ ] 连续重开 10 次后，水管数量保持有界，无旧对象残留和分数残留。
- [ ] 最高分在关闭并重启后仍存在，各工程使用独立存储键或目录。
- [ ] 1024×768、1280×720 和竖向窗口下保持比例，逻辑玩法范围不变。
- [ ] 后台切换不会偷跑逻辑，恢复操作不会误触起飞或立即死亡。
- [ ] 同一 fixture 指定 tick 的截图可以与 Phaser 基准对照。

最终结果写入 `docs/acceptance.md`：标明实际引擎版本、运行平台、启动命令、构建结果、检查项与已知限制。桌面导出、Web 构建和触摸检查只在实际验证后标记通过；不以编译成功替代可玩验收。
